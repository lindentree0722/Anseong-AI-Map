# 함께 만드는 웹 프로젝트: Git 협업과 페이지 공유

2026년 11월 18일 수업 정리 · 개발을 처음 배우는 학생용

목표: **내 작업을 안전하게 올리고, 친구의 변경을 받아오고, 완성한 화면을 공유하기.**

## 1. 먼저 알아둘 말

| 용어 | 쉬운 뜻 |
| --- | --- |
| Git | 코드의 변경 이력을 기록하는 도구 |
| GitHub | Remote Repository(원격 리포지토리)를 보관하고 팀과 공유하는 서비스 |
| Repository(리포지토리) | 프로젝트 파일과 Git 변경 이력을 담는 저장소 |
| Remote(원격) / Local(로컬) | 인터넷에 있는 쪽 / 내 컴퓨터에 있는 쪽 |
| main | 팀이 함께 사용하는 기준 Branch(분기) |
| Branch(분기) | 기준 코드에서 갈라져 내 작업을 진행하는 작업 공간 |
| Commit(커밋) | 변경 내용을 설명과 함께 기록한 저장 지점 |
| Push(푸시) / Pull(풀) | 내 Commit(커밋) 올리기 / 원격 변경을 가져와 반영하기 |
| Pull Request(끌어오기 요청, PR) | “내 변경을 확인하고 main에 합쳐 주세요”라는 요청 |
| Merge(병합) | 두 Branch(분기)의 변경을 합치는 작업 |

파일 저장 → Commit(커밋) → Push(푸시)는 서로 다릅니다. **저장만 하면 GitHub에는 올라가지 않습니다. Push(푸시)해도 main에 자동으로 합쳐지지 않습니다.**

아래 명령은 Git과 프로젝트가 준비된 상태에서, 프로젝트 폴더를 연 Terminal(터미널)에 한 줄씩 입력합니다. 예시의 `sy`는 내 이니셜로 바꾸세요.

### VS Code에서 보이는 이름과 연결하기

영어 메뉴 이름 뒤에 한글 뜻을 붙였습니다. Git 용어는 VS Code 표현을 우선하며, 한글 메뉴는 버전과 언어 팩에 따라 조금 다를 수 있습니다. 명령어와 실제 Branch(분기) 이름은 번역하지 않고 그대로 입력합니다.

| VS Code 표시 | 하는 일 / 연결되는 명령 |
| --- | --- |
| Source Control(소스 제어) | Git 변경을 확인하는 화면 |
| Changes(변경 내용) | 아직 스테이징하지 않은 수정 파일 |
| Stage Changes(변경 내용 스테이징) | 다음 기록에 담을 파일 선택: `git add` |
| Staged Changes(스테이징된 변경 내용) | 다음 기록에 담기로 선택한 파일 |
| Commit(커밋) | 선택한 변경 기록: `git commit` |
| Create Branch(분기 만들기) | 새 작업 공간 만들기: `git switch -c` |
| Fetch(페치) | 원격 기록만 가져오기: `git fetch` |
| Pull(풀) | 연결된 원격 분기 변경을 가져와 반영: `git pull` |
| Push(푸시) | 내 기록 올리기: `git push` |
| Sync Changes(변경 내용 동기화) | 연결된 원격 분기에서 Pull(풀)한 뒤 Push(푸시) |

**Sync Changes(변경 내용 동기화)는 main을 내 Branch(분기)에 합치는 버튼이 아닙니다.** main 변경을 반영하는 방법은 4절을 따릅니다. [VS Code 공식 Git 시작 안내](https://code.visualstudio.com/docs/sourcecontrol/quickstart)

## 2. Branch(분기) 이름은 이렇게 약속하기

우리 팀은 `작업종류-이니셜/짧은-작업내용` 형식을 사용해 봅시다. Git의 강제 규칙이 아니라 팀 약속입니다.

| 작업 | 예시 |
| --- | --- |
| 새 기능 | `feat-sy/map-search` |
| 오류 수정 | `fix-sy/map-error` |
| 문서 작성 | `docs-sy/class-notes` |

영문 소문자와 하이픈을 쓰면 편합니다. **한 Branch(분기)에는 한 가지 목적**만 담고, main에서 바로 기능 작업을 하지 않습니다. 이번 수업 기록 Branch(분기)는 요청한 `feat-sy/` 형식을 따릅니다.

## 3. 새 Branch(분기) 만들고 Push(푸시)하기

### ① 내 상태 확인 → 최신 main 받기 → Branch(분기) 만들기

```sh
git status
git switch main
git pull --ff-only origin main
git switch -c feat-sy/map-search
```

첫 `git status`에서 수정 파일이 보이면 먼저 내용을 확인하고 Commit(커밋)한 뒤 진행하세요. `--ff-only`는 기록이 엇갈렸을 때 자동으로 합치지 않고 멈추는 옵션입니다. 실패하면 다음 명령으로 넘어가지 말고 원인을 확인합니다. 이미 있는 Branch(분기)로 이동할 때는 `-c` 없이 `git switch feat-sy/map-search`을 씁니다.

### ② 파일 수정 → 변경 확인 → Commit(커밋)

다음은 README를 수정한 예시입니다. 실제로 작업한 파일 이름으로 바꾸세요.

```sh
git status
git diff -- README.md
git diff --cached -- README.md
git add README.md
git commit -m "프로젝트 실행 안내 추가" -- README.md
```

`git add`는 VS Code의 Stage Changes(변경 내용 스테이징)에 해당하며, 이번 Commit(커밋)에 담을 파일을 고르는 단계입니다. 필요한 파일만 지정하세요. 여러 파일이면 `git add`와 `git commit`의 파일 목록에 모두 적습니다. Commit(커밋) 메시지는 “수정”보다는 **무엇을 바꿨는지** 적습니다.

### ③ 내 Branch(분기)를 GitHub에 올리기

```sh
git push -u origin feat-sy/map-search
```

`origin`은 Remote Repository(원격 리포지토리)의 별명입니다. 첫 Push(푸시)의 `-u`로 내 Branch(분기)와 원격 Branch(분기)를 연결하면, 이후에는 `git push`로 올릴 수 있습니다. `git status`가 `working tree clean`이어도 아직 Push(푸시)하지 않은 Commit(커밋)은 있을 수 있습니다.

> AI에게: “Git을 처음 배워. 현재 `git status` 결과는 다음과 같아. 내 변경을 보존하면서 새 Branch(분기)를 만들고 지정한 파일만 Commit(커밋)하는 순서를 설명해 줘. 명령마다 의미도 알려 줘.”

## 4. 작업 중 main에 친구의 변경이 생겼다면? ★

예: 나는 검색 기능을 만드는 중이고, 친구의 지도 수정이 main에 먼저 합쳐졌습니다. **내 작업 Branch(분기)에 머문 채 최신 main을 합치면 됩니다.**

먼저 내 수정 파일을 확인하고 Commit(커밋)해 작업 폴더를 Clean(미커밋 변경 없음) 상태로 만듭니다. 이후 실행합니다.

```sh
git branch --show-current
git fetch origin
git merge origin/main -m "최신 main 변경 반영"
```

첫 줄이 내 작업 Branch(분기)인지 확인하세요. Fetch(페치)는 원격의 최신 기록만 가져옵니다. `origin/main`은 마지막 Fetch(페치)로 확인한 원격 main이며, Merge(병합)가 그 내용을 **현재 Branch(분기)에** 합칩니다. Local(로컬) main으로 이동할 필요는 없습니다.

합친 다음 앱을 실행하거나 테스트해서 확인하고 올립니다.

```sh
git status
git push
```

**그냥 `git pull`을 하면 보통 연결된 내 원격 작업 Branch(분기)를 받습니다. main을 가져오는 것과 다릅니다.** 같은 작업 Branch(분기)를 여러 컴퓨터에서 쓸 때는 Clean(미커밋 변경 없음) 상태에서 `git pull --ff-only`로 갱신할 수 있습니다. 실패하면 강제 Push(푸시)하지 말고 기록 차이를 확인하세요.

### Merge Conflict(병합 충돌)이 나면

Conflict(충돌)은 같은 부분을 서로 다르게 수정해 Git이 선택하지 못한 상태입니다. 코드가 사라졌다는 뜻은 아닙니다.

1. `git status`로 Conflict(충돌) 파일을 확인합니다.
2. 친구와 두 변경의 의도를 확인합니다. 내 코드나 친구 코드를 무조건 전부 선택하지 않습니다.
3. 파일 안의 `<<<<<<<`, `=======`, `>>>>>>>` 표시를 정리하고, 최종 내용을 직접 확인합니다.
4. `git add 충돌해결한파일`로 해결 표시를 합니다. Conflict(충돌) 파일이 여러 개면 모두 처리합니다.
5. `git status`로 해결 여부와 Merge(병합) 내용을 확인한 뒤 `git commit -m "main 병합 충돌 해결"`을 실행합니다.
6. 동작을 확인하고 `git push`합니다. Merge(병합) 완료 Commit(커밋)은 예외적으로 파일 목록 없이 실행합니다.

해결을 중단하려면 `git merge --abort`를 사용합니다. Merge(병합) 전에 Clean(미커밋 변경 없음) 상태였다면 시작 전 상태로 돌아갈 수 있습니다. Merge(병합) 도중에는 다른 작업을 섞지 마세요. 참고: [Git 공식 Merge(병합) 안내](https://git-scm.com/docs/git-merge).

> AI에게: “나는 `feat-sy/map-search`에서 작업 중이고 최신 `origin/main`을 합치려 해. 내 Commit(커밋)과 친구의 코드를 모두 보존해야 해. 아래 상태와 Conflict(충돌) 부분을 보고 두 변경의 차이를 설명하고 해결안을 제안해 줘. `reset --hard`나 강제 Push(푸시)는 사용하지 마.”

## 5. PR(끌어오기 요청) 만들기와 서로 조심할 점

Push(푸시)한 뒤 GitHub Repository(리포지토리)의 **Pull requests(끌어오기 요청) → New pull request(새 끌어오기 요청)**에서 `base: main`, `compare`에 내 Branch(분기)를 선택합니다. 제목과 설명을 작성하고 친구에게 검토를 요청합니다. 승인과 확인을 마친 뒤 팀에서 정한 사람이 Merge(병합)합니다.

PR(끌어오기 요청) 설명 예시:

```text
제목: 지도에서 장소 검색 기능 추가
변경: 검색어를 입력하면 일치하는 장소를 표시합니다.
확인: 검색 성공, 결과 없음, 빈 입력을 확인했습니다.
미완성: 오타 교정은 아직 지원하지 않습니다.
```

| 올리는 사람이 확인할 것 | 검토하는 사람이 확인할 것 |
| --- | --- |
| main과 내 Branch(분기) 방향이 맞는지 | 설명한 기능이 실제 변경과 맞는지 |
| Files changed(변경된 파일)에 내 작업만 있는지 | 친구가 만든 기존 기능도 동작하는지 |
| 비밀번호·비밀 API(응용 프로그램 인터페이스) 키·`.env`가 없는지 | 비밀 정보나 불필요한 파일이 없는지 |
| 실행·테스트 결과와 미완성 부분을 적었는지 | 이해 안 되는 코드를 질문했는지 |
| main을 합친 후 다시 확인했는지 | Conflict(충돌) 해결 과정에서 코드가 빠지지 않았는지 |

- 같은 파일을 고칠 예정이면 먼저 이야기하세요. 작은 PR(끌어오기 요청)이 검토와 Conflict(충돌) 해결에 유리합니다.
- 친구 PR(끌어오기 요청)이 먼저 합쳐졌다면 내 Branch(분기)도 최신 main을 반영하고 다시 확인합니다.
- 승인 후 코드를 더 수정하면 다시 검토를 요청합니다. 열린 PR(끌어오기 요청)은 같은 Branch(분기)에 Push(푸시)하면 자동 갱신됩니다.
- `node_modules`, 빌드 결과물, 관계없는 수정은 넣지 않습니다. 필요한 `.gitignore` 설정을 확인합니다.
- `push --force`나 기록을 지우는 명령은 혼자 실행하지 않습니다. PR(끌어오기 요청)이 합쳐지면 다음 작업은 최신 main에서 새 Branch(분기)로 시작합니다.

> AI에게: “아래 PR(끌어오기 요청) 변경을 초보자 눈높이로 검토해 줘. 버그 가능성, 친구 기능에 미칠 영향, 비밀 정보 포함 여부, 확인할 테스트를 알려 줘. 코드를 임의로 바꾸지 말고 이유부터 설명해 줘.”

## 6. 같은 LAN(근거리 통신망)에서 친구에게 페이지 보여 주기

**Frontend(프런트엔드)**는 브라우저에 보이는 화면, **Backend(백엔드)**는 데이터를 처리하는 서버, **API(응용 프로그램 인터페이스)**는 둘이 정보를 주고받는 통로입니다.

LAN(근거리 통신망)은 같은 공유기 안의 가까운 Network(네트워크)입니다. 같은 교실에 있어도 서로 다른 Wi-Fi나 게스트망이면 연결되지 않을 수 있습니다. **같은 인터넷을 쓴다는 것만으로 기기끼리 접속할 수 있는 것은 아닙니다.**

### 이 프로젝트에서 공유하기

이미 Frontend(프런트엔드) 서버가 실행 중이면 해당 Terminal(터미널)에서 `Ctrl+C`로 종료합니다. Node.js와 의존성 설치가 되어 있다는 전제에서, 프로젝트 루트에서 실행합니다.

```sh
npm --prefix frontend run dev -- --host 0.0.0.0 --port 5173 --strictPort
```

`0.0.0.0`은 다른 기기의 연결도 받겠다는 실행 설정입니다. 친구에게 줄 주소가 아닙니다. Terminal(터미널)의 **Network(네트워크)** 주소를 복사해 주세요. 예를 들어 `http://192.168.0.19:5173`입니다. 실제 주소는 내 컴퓨터에 표시된 것을 사용합니다. [Vite 공식 안내](https://vite.dev/config/server-options#server-host)

- 친구도 같은 LAN(근거리 통신망)에 연결한 뒤 그 주소를 브라우저에 입력합니다.
- `localhost`와 `127.0.0.1`은 **접속하는 사람 자신의 컴퓨터**입니다. 친구에게 localhost 주소를 주면 내 컴퓨터에 접속되지 않습니다.
- `5173`은 프로그램의 접속 번호인 Port(포트)입니다. Port(포트) 사용 중 오류가 나면 기존 실행을 확인하고 종료하세요.
- 공유 중에는 내 컴퓨터와 서버를 켜 두고, 끝나면 `Ctrl+C`로 종료합니다.
- 접속이 안 되면 IP·Port(포트), 같은 Wi-Fi인지, 방화벽의 해당 앱 수신 허용, 학교 공유기의 기기 간 통신 차단을 순서대로 확인합니다. 방화벽 전체를 끄지 마세요.

### 화면은 열리는데 API(응용 프로그램 인터페이스)가 안 된다면?

화면 서버와 API(응용 프로그램 인터페이스) 서버는 별개입니다. 이 프로젝트의 메인 API(응용 프로그램 인터페이스)는 별도 Terminal(터미널)에서 실행합니다. Python·uv·의존성 준비가 필요합니다.

```sh
uv run --project backend uvicorn main:app --app-dir backend --host 127.0.0.1 --port 8000
```

현재 Frontend(프런트엔드) 개발 서버는 교통 API(응용 프로그램 인터페이스) 요청을 내 컴퓨터의 8000번 서버로 대신 전달합니다. 이를 **Proxy(프록시)**라고 합니다. 따라서 이 방식에서는 Backend(백엔드)의 `127.0.0.1`을 바꿀 필요가 없습니다. 신호 진단 API(응용 프로그램 인터페이스)는 별도 서버가 필요하며 기본 대상 Port(포트)는 8001입니다.

다른 프로젝트에서 친구 브라우저가 API(응용 프로그램 인터페이스)에 직접 접속한다면 Backend(백엔드)도 LAN(근거리 통신망) 연결을 받도록 실행하고, API(응용 프로그램 인터페이스) 주소를 서버 컴퓨터의 LAN(근거리 통신망) IP로 설정해야 합니다. 이때 **CORS(교차 출처 리소스 공유)**라는 “다른 주소의 화면에서 API(응용 프로그램 인터페이스)를 호출해도 되는지” 설정도 필요할 수 있습니다. 비밀 키는 브라우저 코드에 넣지 않습니다.

> AI에게: “React/Vite 화면을 같은 Wi-Fi 친구에게 보여 주고 싶어. 내 OS(운영체제)는 ○○, 화면 Port(포트)는 5173, API(응용 프로그램 인터페이스) Port(포트)는 8000이야. 현재 실행 명령과 오류는 아래와 같아. IP·서버 실행 주소·Proxy(프록시)·CORS(교차 출처 리소스 공유) 중 무엇을 확인해야 할지 순서대로 설명해 줘.”

## 7. 집에서도 접속하려면: 무료 Hosting(호스팅) 선택

**Hosting(호스팅)**은 내 컴퓨터 대신 인터넷의 서버에 앱을 올려 주소를 공유하는 것입니다. 무료에도 사용량·기능 제한이 있습니다. 아래는 **2026-11-18 공식 안내 확인 기준**이며, 가입할 때 최신 조건을 다시 확인하세요.

| 플랫폼 | 화면과 Backend(백엔드) | 무료 조건과 수업용 판단 |
| --- | --- | --- |

### 배포 전에 AI와 확인할 것

이 프로젝트의 Vite Proxy(프록시)는 개발 서버용이라, 인터넷에 화면만 올린다고 API(응용 프로그램 인터페이스) 연결까지 완성되지는 않습니다. 배포용 API(응용 프로그램 인터페이스) 주소·연결 설정과 Python 버전 지원을 확인해야 합니다. 무료 한도와 외부 AI API(응용 프로그램 인터페이스) 사용료도 별개입니다.

> AI에게: “고등학생 수업 프로젝트야. React/Vite Frontend(프런트엔드)와 Python/FastAPI Backend(백엔드)를 무료로 배포하고 싶어. 결제 카드 없이 가능한 구성을 우선 추천해 줘. 현재 폴더 구조와 설정을 보고 빌드 명령, 실행 명령, 환경변수, API(응용 프로그램 인터페이스) 연결, CORS(교차 출처 리소스 공유), 새로고침 경로 설정을 단계별로 알려 줘. 무료 한도·절전·데이터 유지 조건은 최신 공식 링크로 확인해 줘. 유료 전환이나 실제 배포 전에는 먼저 설명해 줘.”

## 8. AI에게 질문할 때 붙이면 좋은 정보

**하려는 일 + 현재 상태 + 실행한 명령 + 오류 원문 + 지켜야 할 조건**을 함께 주면 답이 정확해집니다. 오류의 마지막 한 줄만 주기보다 앞뒤 내용을 함께 보여 주세요. 비밀번호·비밀 키·개인정보는 가립니다.

```text
목표: 친구의 main 변경을 내 브랜치에 가져오고 싶어.
환경: Windows, Git 사용 중.
현재 상태: git status / git branch --show-current 결과는 아래와 같아.
실행한 명령과 오류: ...
조건: 내 작업과 친구 코드를 보존해야 해. 삭제나 강제 push는 하지 마.
요청: 초보자가 한 단계씩 확인할 수 있도록 명령과 예상 결과를 설명해 줘.
```

AI가 준 명령도 먼저 뜻을 확인하세요. 실행 결과가 예상과 다르면 멈추고 그 결과를 다시 질문합니다.
