# 함께 만드는 웹 프로젝트: Git 협업과 페이지 공유

2026년 11월 18일 수업 정리 · 개발을 처음 배우는 학생용

목표: **내 작업을 안전하게 올리고, 친구의 변경을 받아오고, 완성한 화면을 공유하기.**

## 1. 먼저 알아둘 말

| 용어 | 쉬운 뜻 |
| --- | --- |
| Git | 코드의 변경 이력을 기록하는 도구 |
| GitHub / 원격 저장소 | 팀이 코드를 올려 공유하는 인터넷 저장소 |
| 로컬 | 내 컴퓨터에 있는 프로젝트 |
| main | 팀이 함께 사용하는 기준 브랜치 |
| 브랜치 | 기준 코드에서 갈라져 내 작업을 진행하는 작업 공간 |
| commit | 변경 내용을 설명과 함께 기록한 저장 지점 |
| push / pull | 내 커밋 올리기 / 원격 변경을 가져와 반영하기 |
| PR(Pull Request) | “내 변경을 확인하고 main에 합쳐 주세요”라는 요청 |
| merge | 두 브랜치의 변경을 합치는 작업 |

파일 저장 → commit → push는 서로 다릅니다. **저장만 하면 GitHub에는 올라가지 않습니다. push해도 main에 자동으로 합쳐지지 않습니다.**

아래 명령은 Git과 프로젝트가 준비된 상태에서, 프로젝트 폴더를 연 터미널에 한 줄씩 입력합니다. 예시의 `sy`는 내 이니셜로 바꾸세요.

## 2. 브랜치 이름은 이렇게 약속하기

우리 팀은 `작업종류-이니셜/짧은-작업내용` 형식을 사용해 봅시다. Git의 강제 규칙이 아니라 팀 약속입니다.

| 작업 | 예시 |
| --- | --- |
| 새 기능 | `feat-sy/map-search` |
| 오류 수정 | `fix-sy/map-error` |
| 문서 작성 | `docs-sy/class-notes` |

영문 소문자와 하이픈을 쓰면 편합니다. **한 브랜치에는 한 가지 목적**만 담고, main에서 바로 기능 작업을 하지 않습니다. 이번 수업 기록 브랜치는 요청한 `feat-sy/` 형식을 따릅니다.

## 3. 새 브랜치 만들고 push하기

### ① 내 상태 확인 → 최신 main 받기 → 브랜치 만들기

```sh
git status
git switch main
git pull --ff-only origin main
git switch -c feat-sy/map-search
```

첫 `git status`에서 수정 파일이 보이면 먼저 내용을 확인하고 커밋한 뒤 진행하세요. `--ff-only`는 기록이 엇갈렸을 때 자동으로 합치지 않고 멈추는 옵션입니다. 실패하면 다음 명령으로 넘어가지 말고 원인을 확인합니다. 이미 있는 브랜치로 이동할 때는 `-c` 없이 `git switch 브랜치이름`을 씁니다.

### ② 파일 수정 → 변경 확인 → commit

다음은 README를 수정한 예시입니다. 실제로 작업한 파일 이름으로 바꾸세요.

```sh
git status
git diff -- README.md
git diff --cached -- README.md
git add README.md
git commit -m "프로젝트 실행 안내 추가" -- README.md
```

`add`는 이번 기록에 담을 파일을 고르는 단계입니다. 필요한 파일만 지정하세요. 여러 파일이면 `git add`와 `git commit`의 파일 목록에 모두 적습니다. 커밋 메시지는 “수정”보다는 **무엇을 바꿨는지** 적습니다.

### ③ 내 브랜치를 GitHub에 올리기

```sh
git push -u origin feat-sy/map-search
```

`origin`은 원격 저장소의 별명입니다. 첫 push의 `-u`로 내 브랜치와 원격 브랜치를 연결하면, 이후에는 `git push`로 올릴 수 있습니다. `git status`가 `working tree clean`이어도 아직 push하지 않은 커밋은 있을 수 있습니다.

> AI에게: “Git을 처음 배워. 현재 `git status` 결과는 다음과 같아. 내 변경을 보존하면서 새 브랜치를 만들고 지정한 파일만 커밋하는 순서를 설명해 줘. 명령마다 의미도 알려 줘.”

## 4. 작업 중 main에 친구의 변경이 생겼다면? ★

예: 나는 검색 기능을 만드는 중이고, 친구의 지도 수정이 main에 먼저 합쳐졌습니다. **내 작업 브랜치에 머문 채 최신 main을 합치면 됩니다.**

먼저 내 수정 파일을 확인하고 커밋해 작업 폴더를 clean 상태로 만듭니다. 이후 실행합니다.

```sh
git branch --show-current
git fetch origin
git merge origin/main -m "최신 main 변경 반영"
```

첫 줄이 내 작업 브랜치인지 확인하세요. `fetch`는 원격의 최신 기록만 가져옵니다. `origin/main`은 마지막 fetch로 확인한 원격 main이며, `merge`가 그 내용을 **현재 브랜치에** 합칩니다. 로컬 main으로 이동할 필요는 없습니다.

합친 다음 앱을 실행하거나 테스트해서 확인하고 올립니다.

```sh
git status
git push
```

**그냥 `git pull`을 하면 보통 연결된 내 원격 작업 브랜치를 받습니다. main을 가져오는 것과 다릅니다.** 같은 작업 브랜치를 여러 컴퓨터에서 쓸 때는 clean 상태에서 `git pull --ff-only`로 갱신할 수 있습니다. 실패하면 강제 push하지 말고 기록 차이를 확인하세요.

### 충돌(CONFLICT)이 나면

충돌은 같은 부분을 서로 다르게 수정해 Git이 선택하지 못한 상태입니다. 코드가 사라졌다는 뜻은 아닙니다.

1. `git status`로 충돌 파일을 확인합니다.
2. 친구와 두 변경의 의도를 확인합니다. 내 코드나 친구 코드를 무조건 전부 선택하지 않습니다.
3. 파일 안의 `<<<<<<<`, `=======`, `>>>>>>>` 표시를 정리하고, 최종 내용을 직접 확인합니다.
4. `git add 충돌해결한파일`로 해결 표시를 합니다. 충돌 파일이 여러 개면 모두 처리합니다.
5. `git status`로 해결 여부와 병합 내용을 확인한 뒤 `git commit -m "main 병합 충돌 해결"`을 실행합니다.
6. 동작을 확인하고 `git push`합니다. 병합 완료 커밋은 예외적으로 파일 목록 없이 실행합니다.

해결을 중단하려면 `git merge --abort`를 사용합니다. 병합 전에 clean 상태였다면 시작 전 상태로 돌아갈 수 있습니다. 병합 도중에는 다른 작업을 섞지 마세요. 참고: [Git 공식 병합 안내](https://git-scm.com/docs/git-merge).

> AI에게: “나는 `feat-sy/map-search`에서 작업 중이고 최신 `origin/main`을 합치려 해. 내 커밋과 친구의 코드를 모두 보존해야 해. 아래 상태와 충돌 부분을 보고 두 변경의 차이를 설명하고 해결안을 제안해 줘. `reset --hard`나 강제 push는 사용하지 마.”

## 5. PR 만들기와 서로 조심할 점

push한 뒤 GitHub 저장소의 **Pull requests → New pull request**에서 `base: main`, `compare: 내 브랜치`를 선택합니다. 제목과 설명을 작성하고 친구에게 검토를 요청합니다. 승인과 확인을 마친 뒤 팀에서 정한 사람이 Merge합니다.

PR 설명 예시:

```text
제목: 지도에서 장소 검색 기능 추가
변경: 검색어를 입력하면 일치하는 장소를 표시합니다.
확인: 검색 성공, 결과 없음, 빈 입력을 확인했습니다.
미완성: 오타 교정은 아직 지원하지 않습니다.
```

| 올리는 사람이 확인할 것 | 검토하는 사람이 확인할 것 |
| --- | --- |
| main과 내 브랜치 방향이 맞는지 | 설명한 기능이 실제 변경과 맞는지 |
| Files changed에 내 작업만 있는지 | 친구가 만든 기존 기능도 동작하는지 |
| 비밀번호·비밀 API 키·`.env`가 없는지 | 비밀 정보나 불필요한 파일이 없는지 |
| 실행·테스트 결과와 미완성 부분을 적었는지 | 이해 안 되는 코드를 질문했는지 |
| main을 합친 후 다시 확인했는지 | 충돌 해결 과정에서 코드가 빠지지 않았는지 |

- 같은 파일을 고칠 예정이면 먼저 이야기하세요. 작은 PR이 검토와 충돌 해결에 유리합니다.
- 친구 PR이 먼저 합쳐졌다면 내 브랜치도 최신 main을 반영하고 다시 확인합니다.
- 승인 후 코드를 더 수정하면 다시 검토를 요청합니다. 열린 PR은 같은 브랜치에 push하면 자동 갱신됩니다.
- `node_modules`, 빌드 결과물, 관계없는 수정은 넣지 않습니다. 필요한 `.gitignore` 설정을 확인합니다.
- `push --force`나 기록을 지우는 명령은 혼자 실행하지 않습니다. PR이 합쳐지면 다음 작업은 최신 main에서 새 브랜치로 시작합니다.

> AI에게: “아래 PR 변경을 초보자 눈높이로 검토해 줘. 버그 가능성, 친구 기능에 미칠 영향, 비밀 정보 포함 여부, 확인할 테스트를 알려 줘. 코드를 임의로 바꾸지 말고 이유부터 설명해 줘.”

## 6. 같은 LAN에서 친구에게 페이지 보여 주기

**프런트엔드**는 브라우저에 보이는 화면, **백엔드**는 데이터를 처리하는 서버, **API**는 둘이 정보를 주고받는 통로입니다.

LAN은 같은 공유기 안의 가까운 네트워크입니다. 같은 교실에 있어도 서로 다른 Wi-Fi나 게스트망이면 연결되지 않을 수 있습니다. **같은 인터넷을 쓴다는 것만으로 기기끼리 접속할 수 있는 것은 아닙니다.**

### 이 프로젝트에서 공유하기

이미 프런트 서버가 실행 중이면 해당 터미널에서 `Ctrl+C`로 종료합니다. Node.js와 의존성 설치가 되어 있다는 전제에서, 프로젝트 루트에서 실행합니다.

```sh
npm --prefix frontend run dev -- --host 0.0.0.0 --port 5173 --strictPort
```

`0.0.0.0`은 다른 기기의 연결도 받겠다는 실행 설정입니다. 친구에게 줄 주소가 아닙니다. 터미널의 **Network** 주소를 복사해 주세요. 예를 들어 `http://192.168.0.19:5173`입니다. 실제 주소는 내 컴퓨터에 표시된 것을 사용합니다. [Vite 공식 안내](https://vite.dev/config/server-options#server-host)

- 친구도 같은 LAN에 연결한 뒤 그 주소를 브라우저에 입력합니다.
- `localhost`와 `127.0.0.1`은 **접속하는 사람 자신의 컴퓨터**입니다. 친구에게 localhost 주소를 주면 내 컴퓨터에 접속되지 않습니다.
- `5173`은 프로그램의 접속 번호인 포트입니다. 포트 사용 중 오류가 나면 기존 실행을 확인하고 종료하세요.
- 공유 중에는 내 컴퓨터와 서버를 켜 두고, 끝나면 `Ctrl+C`로 종료합니다.
- 접속이 안 되면 IP·포트, 같은 Wi-Fi인지, 방화벽의 해당 앱 수신 허용, 학교 공유기의 기기 간 통신 차단을 순서대로 확인합니다. 방화벽 전체를 끄지 마세요.

### 화면은 열리는데 API가 안 된다면?

화면 서버와 API 서버는 별개입니다. 이 프로젝트의 메인 API는 별도 터미널에서 실행합니다. Python·uv·의존성 준비가 필요합니다.

```sh
uv run --project backend uvicorn main:app --app-dir backend --host 127.0.0.1 --port 8000
```

현재 프런트 개발 서버는 교통 API 요청을 내 컴퓨터의 8000번 서버로 대신 전달합니다. 이를 **프록시**라고 합니다. 따라서 이 방식에서는 백엔드의 `127.0.0.1`을 바꿀 필요가 없습니다. 신호 진단 API는 별도 서버가 필요하며 기본 대상 포트는 8001입니다.

다른 프로젝트에서 친구 브라우저가 API에 직접 접속한다면 백엔드도 LAN 연결을 받도록 실행하고, API 주소를 서버 컴퓨터의 LAN IP로 설정해야 합니다. 이때 **CORS**라는 “다른 주소의 화면에서 API를 호출해도 되는지” 설정도 필요할 수 있습니다. 비밀 키는 브라우저 코드에 넣지 않습니다.

> AI에게: “React/Vite 화면을 같은 Wi-Fi 친구에게 보여 주고 싶어. 내 OS는 ○○, 화면 포트는 5173, API 포트는 8000이야. 현재 실행 명령과 오류는 아래와 같아. IP·서버 실행 주소·프록시·CORS 중 무엇을 확인해야 할지 순서대로 설명해 줘.”

## 7. 집에서도 접속하려면: 무료 호스팅 선택

**호스팅**은 내 컴퓨터 대신 인터넷의 서버에 앱을 올려 주소를 공유하는 것입니다. 무료에도 사용량·기능 제한이 있습니다. 아래는 **2026-11-18 공식 안내 확인 기준**이며, 가입할 때 최신 조건을 다시 확인하세요.

| **Firebase** | Hosting으로 화면, Firestore·Authentication으로 저장·로그인 기능 구성 | Spark는 결제 수단 없이 무료 한도를 제공합니다. 직접 만든 백엔드를 올리는 Cloud Functions나 App Hosting은 Blaze 결제 플랜이 필요합니다. **기존 Python API를 결제 없이 그대로 올릴 용도로는 추천하지 않습니다.** [요금표](https://firebase.google.com/pricing), [App Hosting 비용](https://firebase.google.com/docs/app-hosting/costs) |

**이번 프로젝트의 첫 배포는 Render에 화면과 API를 각각 만드는 방식**을 추천합니다. 화면만 먼저 보여 주고 싶다면 Vercel도 선택지입니다. Firebase는 직접 서버를 만드는 대신 제공되는 저장·로그인 기능을 활용하고 싶을 때 살펴보세요. 이는 위 조건과 현재 프로젝트 구조를 바탕으로 한 추천입니다.

무료 서버의 메모리나 임시 파일에 저장한 데이터는 재시작 때 사라질 수 있습니다. 중요한 자료는 별도 영구 저장소가 필요합니다. Render 무료 Postgres는 30일 뒤 만료되므로 장기 보관용으로 생각하지 마세요. [무료 서비스 제한](https://render.com/docs/free)

### 배포 전에 AI와 확인할 것

이 프로젝트의 Vite 프록시는 개발 서버용이라, 인터넷에 화면만 올린다고 API 연결까지 완성되지는 않습니다. 배포용 API 주소·연결 설정과 Python 버전 지원을 확인해야 합니다. 무료 한도와 외부 AI API 사용료도 별개입니다.

> AI에게: “고등학생 수업 프로젝트야. React/Vite 프런트와 Python/FastAPI 백엔드를 무료로 배포하고 싶어. 결제 카드 없이 가능한 구성을 우선 추천해 줘. 현재 폴더 구조와 설정을 보고 빌드 명령, 실행 명령, 환경변수, API 연결, CORS, 새로고침 경로 설정을 단계별로 알려 줘. 무료 한도·절전·데이터 유지 조건은 최신 공식 링크로 확인해 줘. 유료 전환이나 실제 배포 전에는 먼저 설명해 줘.”

## 8. AI에게 질문할 때 붙이면 좋은 정보

**하려는 일 + 현재 상태 + 실행한 명령 + 오류 원문 + 지켜야 할 조건**을 함께 주면 답이 정확해집니다. 오류의 마지막 한 줄만 주기보다 앞뒤 내용을 함께 보여 주세요. 비밀번호·비밀 키·개인정보는 가립니다.

```text
목표: 친구의 main 변경을 내 브랜치에 가져오고 싶어.
환경: Windows, Git 사용 중.
현재 상태: git status / git branch --show-current 결과는 아래와 같아.
실행한 명령과 오류: ...
조건: 내 작업과 친구 코드를 보존해야 해. 삭제나 강제 push는 하지 마.
요청: 초보자가 한 단계씩 확인할 수 있도록 명령과 예상 결과를 설명해 줘.
```

AI가 준 명령도 먼저 뜻을 확인하세요. 실행 결과가 예상과 다르면 멈추고 그 결과를 다시 질문합니다.
